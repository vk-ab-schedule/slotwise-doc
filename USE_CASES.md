# Пользовательские сценарии SlotWise

**Статусы:**

- **MVP** — входит в обязательный объём;
- **После MVP** — запланированное расширение;
- **Исключён** — сценарий убран, номер сохранён, чтобы не сбивать ссылки.

Номера сценариев не переиспользуются: новые сценарии получают следующий свободный номер.

## Словарь терминов

| Термин | Определение |
| --- | --- |
| Учётная запись | Данные для входа конкретного пользователя: email, хэш пароля, роль, ФИО, признак активности. Создаётся импортом данных вуза или вручную администратором; саморегистрации нет. |
| Роль | Набор разрешённых действий: администратор, организатор, преподаватель или студент. У учётной записи ровно одна роль. |
| Данные вуза | Справочная информация, загружаемая администратором: учётные записи, учебные группы, аудитории, дисциплины, связи «преподаватель — дисциплина — группа» и «студент — научный руководитель», учебное расписание. |
| Сессия планирования | Контейнер с периодом проведения, рабочими днями и часами, часовым поясом, окном сбора занятости, участниками, ресурсами, событиями, правилами и вариантами расписания. Принадлежит создавшему её организатору. |
| Участник сессии | Пользователь, входящий хотя бы в одно событие сессии или в пул комиссии. Только участники заполняют занятость и видят сессию. |
| Пул комиссии | Преподаватели, из которых система подбирает комиссии для событий сессии; часть из них отмечена как возможные председатели. |
| Окно сбора занятости | Период, в течение которого участники отмечают своё занятое время. Заканчивается до начала периода проведения. |
| Известная занятость | Занятость из учебного расписания (пары у людей и аудиторий). Показывается участнику, но не редактируется им; считается критической. |
| Занятый интервал | Время, отмеченное участником как неудобное. У интервала есть уровень важности. |
| Уровень важности | Критический — время нельзя использовать (жёсткое ограничение); средний — использовать нежелательно (мягкое ограничение с большим весом); низкий — предпочтение (мягкое ограничение с малым весом). |
| Доступное время | Время внутри рабочих часов сессии, не покрытое известной занятостью и критическими интервалами участника. |
| Статус ответа | «Не ответил» или «Отправил». Отправить можно и пустой календарь — это значит «ограничений нет». |
| Событие | Единица планирования с длительностью, участниками и требованиями, например консультация группы или защита одного студента. |
| Тип события | Шаблон со значениями по умолчанию: длительностью, гранулярностью (на студента или на группу), ролями участников, требованиями к комиссии и ресурсам, зависимостями. Ведёт администратор. |
| Ресурс | Аудитория или онлайн-площадка с вместимостью, оборудованием и занятостью. |
| Назначение | Дата и время начала, ресурс и состав комиссии, которые система или организатор определили для события. |
| Версия входных данных | Номер, который увеличивается при любом изменении событий, участников, ресурсов, занятости или правил сессии. Позволяет понять, на каких данных рассчитан вариант. |
| Вариант расписания | Набор назначений, полученный одним расчётом (или правкой) на определённой версии входных данных. Статусы: черновик, опубликован, заменён. |
| Фиксация | Запрет менять назначение события при следующих расчётах. Фиксация не публикует событие. |
| Публикация | Выбор варианта действующим. Участники видят только действующий опубликованный вариант. Публикация нового варианта заменяет предыдущий. |
| Запрос на перенос | Сообщение участника о новой недоступности после закрытия сбора; организатор принимает или отклоняет его. |
| Сценарий «что если» | Копия входных данных сессии для эксперимента без изменения рабочего расписания. |

## 1 Доступ и данные вуза

### UX-01 Войти в систему

**Статус:** MVP · **Участник:** любой пользователь

**Цель:** получить доступ к функциям и данным своей роли.

**Предусловия:** учётная запись существует, активна и имеет пароль.

**Основной сценарий**

1. Пользователь вводит email и пароль.
2. Система проверяет данные и открывает раздел, соответствующий роли.

**Результат:** пользователь вошёл и видит только разрешённые его роли данные.

| Ситуация | Решение |
| --- | --- |
| Неверный email или пароль | Одинаковое сообщение об ошибке в обоих случаях, без раскрытия, существует ли учётная запись |
| Учётная запись отключена или у неё нет пароля | Не выполнять вход, предложить обратиться к администратору |
| Сессия входа истекла или завершена администратором | При следующем запросе вернуть на страницу входа |
| Пользователь нажал «Выйти» | Завершить сессию входа на сервере |

### UX-02 Добавить администратора

**Статус:** MVP · **Участник:** администратор

**Цель:** передать административные полномочия ещё одному человеку.

**Предусловия:** в системе есть хотя бы один администратор. Первый администратор создаётся при запуске системы из параметров развёртывания, если администраторов ещё нет.

**Основной сценарий**

1. Администратор создаёт учётную запись вручную (UX-23) или выбирает существующую.
2. Назначает роль «администратор» и подтверждает.

**Результат:** новый администратор может войти и управлять данными вуза.

| Ситуация | Решение |
| --- | --- |
| Email уже занят (при создании новой записи) | Показать существующую учётную запись и предложить сменить её роль |
| Сохранение не удалось | Не менять права, предложить повторить |

### UX-03 Изменить роль или отключить учётную запись

**Статус:** MVP · **Участник:** администратор

**Цель:** выдать пользователю нужную роль или закрыть ему доступ.

**Предусловия:** учётная запись существует.

**Основной сценарий**

1. Администратор находит пользователя и видит его текущую роль и статус.
2. Меняет роль или отключает учётную запись и сохраняет.

**Результат:** изменение действует сразу: все активные сессии входа пользователя завершаются, при следующем входе применяется новая роль.

| Ситуация | Решение |
| --- | --- |
| Пользователь пытается изменить свою роль | Запрещено: менять роли может только администратор, и не себе |
| Операция оставит систему без активного администратора | Заблокировать |
| Пользователь участвует в сессиях, а его роль меняется | Предупредить, в каких сессиях он участвует; данные сессий не удалять |

### UX-04 Загрузить данные вуза из JSON

**Статус:** MVP · **Участник:** администратор

**Цель:** загрузить учётные записи, группы, аудитории, связи и учебное расписание без ручного ввода — так, как если бы они пришли из интеграции с вузом.

**Предусловия:** файл подготовлен по формату из [ARCHITECTURE.md](ARCHITECTURE.md#формат-импорта-данных-вуза).

**Основной сценарий**

1. Администратор загружает JSON-файл.
2. Система проверяет файл и показывает предварительный результат по каждому разделу: новые записи, обновляемые записи, строки с ошибками.
3. Администратор подтверждает импорт.
4. Система создаёт и обновляет записи. Записи сопоставляются по внешнему идентификатору, поэтому повторный импорт того же файла ничего не дублирует.

**Результат:** данные доступны для выбора в сессиях планирования; учётные записи с хэшем пароля могут входить.

| Ситуация | Решение |
| --- | --- |
| Файл не является корректным JSON или не соответствует формату | Не импортировать, показать ошибки с указанием места |
| Ошибки только в части записей | Показать проблемные записи; импортировать остальные только после явного подтверждения |
| Ссылка на несуществующую запись (студент в группе, которой нет) | Считать запись ошибочной |
| У учётной записи нет хэша пароля | Создать запись без возможности входа; пароль задаёт администратор (UX-23) |
| Хэш в неподдерживаемом формате | Считать запись ошибочной |
| Email совпадает с другой учётной записью с иным внешним идентификатором | Считать запись ошибочной, показать конфликт |
| Файл пуст или не содержит изменений | Не запускать импорт, сообщить об этом |

### UX-23 Отредактировать данные вуза вручную

**Статус:** MVP · **Участник:** администратор

**Цель:** точечно поправить данные без повторного импорта: создать учётную запись, задать или сбросить пароль, изменить ФИО, группу, аудиторию, связь.

**Основной сценарий**

1. Администратор открывает нужный раздел данных вуза и выбирает запись или создаёт новую.
2. Меняет поля и сохраняет.

**Результат:** изменения сохранены и видны в сессиях планирования.

| Ситуация | Решение |
| --- | --- |
| Запись используется в событиях сессий | Разрешить правку; повысить версию входных данных затронутых сессий, варианты пометить как устаревшие |
| Удаление записи, используемой в событиях | Запретить удаление; предложить отключение |

### UX-07 Управлять типами событий

**Статус:** MVP · **Участник:** администратор

**Цель:** создать или изменить шаблон для часто повторяющихся событий.

**Основной сценарий**

1. Администратор открывает справочник типов событий.
2. Задаёт:
   - название;
   - длительность по умолчанию (кратна 15 минутам);
   - гранулярность: одно событие на студента или на группу;
   - роли участников: студент или группа, преподаватель дисциплины, научный руководитель;
   - требования к комиссии: нужна ли, размер, нужен ли председатель;
   - формат по умолчанию;
   - требуемое оборудование;
   - зависимости от других типов: например, «предзащита не позже чем за 3 дня до защиты».
3. Сохраняет тип.

**Результат:** тип доступен организаторам при создании событий и подставляет значения по умолчанию. Начальный справочник: экзамен по дисциплине, консультация по дисциплине, консультация с научным руководителем, предзащита, защита.

| Ситуация | Решение |
| --- | --- |
| Изменяется тип, уже использованный в событиях | Созданные события не меняются; новые значения применяются к новым событиям |
| Не хватает обязательных параметров | Не сохранять, перечислить недостающие |
| Зависимости типов образуют цикл | Не сохранять, показать цикл |
| Удаляется тип, по которому есть события | Запретить удаление; предложить скрыть тип из выбора |

## 2 Подготовка планирования

### UX-05 Создать сессию планирования

**Статус:** MVP · **Участник:** организатор

**Цель:** задать границы работы: когда проходят события и когда участники сообщают о занятости.

**Основной сценарий**

1. Организатор задаёт название, период проведения, рабочие дни, рабочие часы и часовой пояс.
2. Указывает начало и конец окна сбора занятости. Окно должно закончиться до начала периода проведения.
3. Сохраняет сессию как черновик и переходит к участникам, ресурсам и событиям.

**Результат:** создан черновик сессии. Сессию видит и редактирует только создавший её организатор.

| Ситуация | Решение |
| --- | --- |
| Период не задан или конец раньше начала | Не сохранять, подсветить поля |
| Окно сбора заканчивается после начала периода | Не сохранять, подсветить поля |
| У организатора уже есть сессия с таким названием | Не сохранять, попросить уточнить название |

### UX-06 Выбрать участников и ресурсы

**Статус:** MVP · **Участник:** организатор

**Цель:** подготовить людей, группы, пул комиссии и аудитории для сессии.

**Предусловия:** сессия создана; данные вуза загружены.

**Основной сценарий**

1. Организатор выбирает учебные группы и отдельных пользователей из данных вуза.
2. Формирует пул комиссии и отмечает возможных председателей.
3. Выбирает аудитории и при необходимости добавляет онлайн-площадку.

**Результат:** в сессии есть участники, пул комиссии и ресурсы, которые можно использовать в событиях.

| Ситуация | Решение |
| --- | --- |
| Нужного пользователя или аудитории нет в данных вуза | Сообщить, что их добавляет администратор (UX-04, UX-23) |
| У студента не указан научный руководитель, а он нужен для выбранного типа событий | Показать проблемные записи; события для них не создавать до исправления |
| Аудитория занята учебным расписанием весь период | Предупредить и предложить другую аудиторию |

### UX-08 Создать события

**Статус:** MVP · **Участник:** организатор

**Цель:** задать все события, которые система должна расположить в периоде.

**Предусловия:** участники и ресурсы выбраны (UX-06), нужные типы событий есть в справочнике.

**Основной сценарий**

1. Организатор выбирает тип и группу или конкретных студентов.
2. Система создаёт события по гранулярности типа (например, по защите на каждого студента группы) и подставляет участников по связям из данных вуза: преподавателя дисциплины, научного руководителя.
3. Организатор при необходимости меняет у отдельных событий длительность, формат, участников, требования к комиссии и оборудованию.
4. Система создаёт зависимости между событиями одного студента по правилам типов.
5. Организатор сохраняет события.

**Результат:** в сессии полный набор событий с требованиями.

| Ситуация | Решение |
| --- | --- |
| Для дисциплины и группы не найден преподаватель | Показать отсутствующую связь, не подставлять случайного участника; событие сохраняется как неполное |
| Один человек выбран несколькими способами | Учитывать его один раз |
| Ручная зависимость образует цикл | Не сохранять зависимость, показать цикл |
| Событие неполное (нет обязательного участника) | Сохранить как неполное; неполные события не участвуют в расчёте, предпроверка их показывает |

### UX-09 Указать занятое время

**Статус:** MVP · **Участник:** участник сессии (студент или преподаватель)

**Цель:** сообщить, когда участие невозможно или нежелательно.

**Предусловия:** окно сбора открыто; пользователь — участник сессии.

**Основной сценарий**

1. Пользователь открывает календарь периода проведения в своём часовом поясе и видит известную занятость из учебного расписания.
2. Добавляет занятые интервалы и указывает для каждого уровень важности: критический, средний или низкий.
3. Отправляет календарь. Если ограничений нет, отправляет его пустым («ограничений нет»).

**Результат:** статус ответа — «Отправил». Неотмеченное время в рабочих часах считается доступным. До закрытия окна пользователь может менять интервалы.

| Ситуация | Решение |
| --- | --- |
| Учебное расписание не загружено | Показать предупреждение; пользователь вносит пары вручную как критические интервалы |
| Интервалы пересекаются | Объединить, применить наивысший уровень важности |
| Интервал выходит за период или рабочие часы | Сохранить только часть внутри периода и рабочих часов |
| Участник отметил всё время как критическое | Сохранить, предупредить, что поставить его события может быть невозможно; организатор увидит это в предпроверке |
| Окно сбора закрыто | Редактирование недоступно; предложить запрос на перенос (UX-19) |

### UX-10 Контролировать сбор занятости

**Статус:** MVP · **Участник:** организатор

**Цель:** понять, кто передал данные и можно ли завершать сбор.

**Предусловия:** окно сбора открыто.

**Основной сценарий**

1. Организатор видит список участников со статусом ответа.
2. Видит неответивших и участников с подозрительными данными: нет ни одного свободного окна.
3. При необходимости продлевает окно (не дальше начала периода) или закрывает его досрочно.

**Результат:** организатор понимает полноту данных перед расчётом.

| Ситуация | Решение |
| --- | --- |
| Участник не ответил | Показывать отдельно. При расчёте считать его доступным в рабочие часы, кроме известной занятости |
| Организатор хочет напомнить | Неответившие видят напоминание при входе в систему; рассылок в MVP нет |
| Срок сбора изменён | Сохранённые ответы не теряются |
| Окно закрыто досрочно | Дальше как в UX-12 |

## 3 Расчёт и публикация

### UX-11 Настроить правила и запустить расчёт вручную

**Статус:** MVP · **Участник:** организатор

**Цель:** настроить мягкие ограничения и получить вариант расписания в любой момент после создания событий, в том числе до закрытия сбора.

**Основной сценарий**

1. Организатор просматривает жёсткие ограничения и задаёт веса мягких.
2. Запускает предпроверку и видит проблемы входных данных.
3. Выбирает алгоритм и лимит времени и запускает расчёт.
4. Наблюдает прогресс и текущее качество.

**Результат:** создан черновой вариант, связанный с версией входных данных, правилами и алгоритмом. Если сбор ещё открыт, вариант помечен «рассчитан на неполных данных».

| Ситуация | Решение |
| --- | --- |
| Предпроверка нашла проблемы | Показать их; запуск разрешён, проблемные события скорее всего останутся неназначенными |
| Лимит истёк, решение найдено | Показать вариант и отметить, что оптимальность не доказана |
| Лимит истёк без решения | Не называть задачу невозможной; предложить больший лимит или другой алгоритм |
| Техническая ошибка | Показать ошибку отдельно от «решения нет», разрешить повторный запуск |
| Уже идёт расчёт этой сессии | Не запускать второй; показать текущий |
| Все слоты расчёта на сервере заняты | Поставить в очередь и показать позицию |

### UX-12 Получить автоматический расчёт после закрытия сбора

**Статус:** После MVP, спринт 3 ([D-15](DECISIONS.md#d-15)); в MVP организатор после закрытия сбора запускает расчёт вручную (UX-11) · **Участник:** система, организатор

**Цель:** получить черновой вариант без ручного запуска.

**Предусловия:** у сессии есть события и правила, окно сбора заканчивается.

**Основной сценарий**

1. В момент окончания окна (или при досрочном закрытии) система закрывает сбор и фиксирует версию входных данных.
2. Система запускает расчёт алгоритмом и лимитом по умолчанию.
3. При следующем входе организатор видит результат: назначения, неназначенные события, список неответивших участников.

**Результат:** черновой вариант для проверки; автоматически он не публикуется.

| Ситуация | Решение |
| --- | --- |
| Не все участники ответили | Всё равно запустить расчёт; неответившие считаются доступными (UX-10), вариант помечен списком неответивших |
| Для этой версии данных уже есть такой же расчёт | Не запускать повторно, показать существующий |
| Автоматический расчёт завершился ошибкой | Показать ошибку организатору, разрешить ручной запуск |

### UX-13 Проверить результат и причины неназначений

**Статус:** MVP · **Участник:** организатор

**Цель:** понять качество варианта, причины конфликтов и последствия возможных правок.

**Предусловия:** есть рассчитанный вариант.

**Основной сценарий**

1. Организатор просматривает календарь по аудиториям, преподавателям или дням, панель метрик и список неназначенных событий.
2. Открывает объяснение по неназначенному событию: какие участники, интервалы, ресурсы или правила помешали.
3. Выбирает событие и видит, какие слоты для него допустимы.

**Результат:** организатор понимает качество варианта.

| Ситуация | Решение |
| --- | --- |
| Вариант рассчитан на устаревшей версии данных | Заметно пометить, предложить пересчитать |
| Точная причина неназначения не установлена | Сообщить об ограниченной диагностике, не утверждать единственную причину. В MVP объяснение строится по предпроверкам; минимальный набор причин — после MVP |
| Оптимальность не доказана | Не использовать слово «оптимальный»; показать метрики и gap, если известен |

### UX-14 Исправить и зафиксировать назначение

**Статус:** MVP · **Участник:** организатор

**Цель:** перенести событие или защитить его от следующего расчёта.

**Предусловия:** есть черновой вариант. Опубликованный вариант не редактируется; изменения после публикации идут через перестроение (UX-20).

**Основной сценарий**

1. Организатор открывает событие и выбирает другое время, ресурс или состав комиссии — через форму или перетаскиванием.
2. Система до сохранения проверяет правку валидатором и показывает нарушения и затронутых участников.
3. Организатор сохраняет допустимую правку и при необходимости фиксирует событие.

**Результат:** правка сохранена в черновом варианте; зафиксированное событие не меняется при следующих расчётах.

| Ситуация | Решение |
| --- | --- |
| Правка нарушает жёсткое ограничение | Не сохранять, показать причину |
| Вариант изменили в другой вкладке после открытия | Отклонить сохранение, предложить обновить |
| После изменения данных зафиксированное событие стало конфликтным | Показать конфликт; снять фиксацию или исправить данные — отдельным действием организатора |
| Перетаскивание недоступно | Правка через форму работает всегда; drag-and-drop — дополнительный способ |

### UX-15 Опубликовать расписание

**Статус:** MVP · **Участник:** организатор

**Цель:** сделать проверенный вариант действующим.

**Предусловия:** организатор выбрал черновой вариант.

**Основной сценарий**

1. Организатор видит итоговую сводку: метрики, неназначенные события, предупреждения.
2. Подтверждает публикацию.
3. Система делает вариант действующим, предыдущий опубликованный помечает как заменённый.

**Результат:** участники видят свои назначения; события, изменённые относительно предыдущей публикации, отмечены.

| Ситуация | Решение |
| --- | --- |
| Вариант нарушает жёсткое ограничение | Публикацию заблокировать, показать события |
| Есть неназначенные события | Явно показать их и потребовать подтверждения. После публикации они остаются в списке у организатора и решаются перестроением (UX-20) |
| Вариант рассчитан на устаревших данных | Предупредить и потребовать подтверждения |
| Запрос публикации повторён | Ничего не менять повторно |

### UX-16 Опубликовать часть расписания

**Статус:** Исключён ([D-08](DECISIONS.md#d-08)). Публикация варианта с неназначенными событиями покрыта UX-15.

## 4 После публикации и развитие

### UX-17 Посмотреть своё расписание

**Статус:** MVP · **Участник:** студент или преподаватель

**Цель:** узнать время, место и состав своих событий.

**Основной сценарий**

1. Пользователь открывает «Моё расписание».
2. Видит события из действующих опубликованных вариантов всех сессий, где он участник: дату, время в своём часовом поясе, формат, аудиторию или онлайн-площадку, ФИО других участников и комиссии.

**Результат:** пользователь знает актуальные сведения о своих событиях.

| Ситуация | Решение |
| --- | --- |
| Назначений нет | Пустое состояние, отличимое от ошибки загрузки |
| Расписание изменилось с прошлого просмотра | Отметить изменённые события |
| Студент запрашивает чужое расписание | Не предоставлять |
| Сведения о других участниках | Только ФИО и роль в событии, без их занятости и контактов |

### UX-18 Экспортировать расписание в календарь

**Статус:** После MVP · **Участник:** студент или преподаватель

**Цель:** добавить события во внешний календарь.

**Основной сценарий**

1. Пользователь выбирает экспорт.
2. Система формирует .ics с корректными часовыми поясами и стабильными идентификаторами событий.
3. Пользователь импортирует файл во внешний календарь.

| Ситуация | Решение |
| --- | --- |
| Опубликованных событий нет | Не создавать файл, объяснить причину |
| Расписание изменилось после скачивания | Предупредить, что файл не обновляется сам; повторный импорт обновит события по их идентификаторам |

### UX-19 Сообщить о новой недоступности

**Статус:** После MVP, спринт 3 ([D-15](DECISIONS.md#d-15)) · **Участники:** студент или преподаватель; организатор

**Цель:** сообщить, что участник больше не может прийти в назначенное время, и получить решение организатора.

**Предусловия:** окно сбора закрыто.

**Основной сценарий**

1. Пользователь указывает период недоступности или конкретное событие и причину.
2. Система показывает затронутые события и отправляет запрос организатору.
3. Организатор видит запрос и затронутые события и принимает или отклоняет его с комментарием.
4. При принятии период недоступности добавляется участнику как критический интервал, и организатор переходит к перестроению (UX-20).

**Результат:** у запроса есть статус, который видит участник; до решения действует прежнее назначение.

| Ситуация | Решение |
| --- | --- |
| Похожий запрос уже открыт | Показать его, не создавать дубликат |
| Событие уже прошло | Не создавать запрос |
| Запрос не рассмотрен | Не скрывать назначение; пометить его у организатора как проблемное |
| Недоступность затрагивает несколько событий | Показать весь список до отправки |

### UX-20 Частично перестроить расписание

**Статус:** После MVP, спринт 3 ([D-15](DECISIONS.md#d-15)) · **Участник:** организатор

**Цель:** найти замену после изменения условий, сохранив остальные назначения.

**Предусловия:** есть действующий опубликованный вариант и изменение: принятый запрос, изменённые данные или неназначенные события.

**Основной сценарий**

1. Организатор видит затронутые события.
2. Запускает перестроение. В базовом режиме все незатронутые события закрепляются, заново расставляются только затронутые и неназначенные. В режиме с минимумом изменений (вау-функция) система может сдвигать и другие события, минимизируя число изменений.
3. Сравнивает предложенный черновой вариант с действующим (diff: что перенесено, у кого сменились время, аудитория или комиссия).
4. Публикует его (UX-15) или отклоняет.

**Результат:** участники видят новую версию с отмеченными изменениями; при отклонении действует прежняя.

| Ситуация | Решение |
| --- | --- |
| Затронутые события поставить не удалось | Показать их и причины; организатор может опубликовать вариант с неназначенными событиями или искать решение вручную |
| Фиксация мешает перестроению | Показать конфликт; снятие фиксации — отдельное действие организатора |
| Предложение отклонено | Действующий вариант не меняется, черновик сохраняется |

### UX-21 Сравнить условия в сценарии «что если»

**Статус:** После MVP · **Участник:** организатор

**Цель:** проверить эффект изменения ресурса, дня или правил без изменения рабочей сессии.

**Основной сценарий**

1. Организатор создаёт сценарий — копию входных данных сессии — и меняет параметр.
2. Запускает расчёт сценария.
3. Сравнивает метрики и назначения с вариантом сессии.

**Результат:** организатор видит эффект изменения; рабочая сессия не меняется.

| Ситуация | Решение |
| --- | --- |
| Расчёт сценария завершился ошибкой | Не затрагивать сессию, разрешить повтор |
| Данные сессии изменились после создания сценария | Показать, что сценарий основан на старой версии, предложить пересоздать |
| Организатор хочет применить результат | Сценарий не публикуется; организатор повторяет изменение в сессии и пересчитывает |

### UX-22 Провести и просмотреть эксперимент алгоритмов

**Статус:** MVP (запуск из командной строки), После MVP (дашборд) · **Участники:** команда; администратор для просмотра дашборда

**Цель:** сравнить качество и время работы алгоритмов на воспроизводимых наборах.

**Основной сценарий**

1. Участник команды запускает консольную программу `experiments` с наборами, seed, алгоритмами и лимитами.
2. Программа прогоняет сетку и сохраняет результаты в CSV.
3. Администратор (после MVP) смотрит таблицы и графики на дашборде экспериментов.

| Ситуация | Решение |
| --- | --- |
| Прогоны на разных входных данных | Не объединять их в прямое сравнение |
| Отдельный прогон завершился ошибкой | Сохранить остальные, пометить неуспешный |
| Результат не проходит валидатор | Исключить из сравнения качества, показать нарушение |
| Третьего алгоритма нет | Сравнивать доступные |
