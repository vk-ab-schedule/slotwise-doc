# Журнал решений

Короткие записи о решениях, которые влияют на продукт, архитектуру или процесс. Решение не переписывается задним числом: если передумали, добавляется новое, а старое помечается «Заменено D-xx».

**Статусы:**
- **Принято** — согласовано командой;
- **Предложено** — ждёт согласования в PR;
- **Заменено** — решение отменено более новым.

## D-01

**Документация живёт в репозитории slotwise-doc** · Предложено · 2026-10-22

Единственный источник правды по проекту — markdown в `slotwise-doc`: изменения проходят через PR, видна история и кто что поменял. Вики репозитория сводится к одной странице со ссылкой на репозиторий, Google Docs больше не ведутся. Две параллельные системы документов быстро расходятся.

## D-02

**Нет саморегистрации; данные вуза загружаются JSON-файлом** · Принято · октябрь 2026

SlotWise не существует сам по себе: он подключается к данным вуза (например, через интеграцию с ITMO ID). Пока интеграций нет, администратор загружает JSON с учётными записями (email, хэш пароля, роль), группами, аудиториями, связями и учебным расписанием — как будто данные пришли из интеграции. Ручное редактирование администратором возможно; массовый ручной ввод не предусмотрен. Заменяет CSV-импорт из первой версии описания.

## D-03

**Пароли в импорте — готовые хэши в формате Spring** · Предложено · 2026-10-22

- **Формат хэша.** `passwordHash` в формате `DelegatingPasswordEncoder` с префиксом алгоритма: `{bcrypt}$2a$10$...`.
- **Поле необязательное.** Без него учётная запись создаётся без возможности входа, пароль задаёт администратор.
- **Первый администратор** создаётся при старте из переменных окружения.
- **Почему так:**
  - открытые пароли нигде не передаются;
  - импорт быстрый, хэшировать при загрузке не нужно;
  - генератор демо-данных выдаёт учётные записи с известными паролями, и на защите разные роли показываются из разных окон браузера;
  - в реальной интеграции вход шёл бы через ITMO ID, и пароли у нас не хранились бы вовсе. Импорт хэшей — эмуляция для демо.

## D-04

**Вход через серверную сессию в cookie, а не JWT** · Предложено · 2026-10-22

Сессии Spring Security хранятся в PostgreSQL (Spring Session JDBC), идентификатор — в HttpOnly-cookie, для изменяющих запросов нужен CSRF-токен.

Почему:
1. **Отзыв прав.** UX-01 и UX-03 требуют мгновенно отзывать доступ при отключении учётной записи или смене роли. С JWT это потребовало бы проверки по БД на каждый запрос или refresh-токенов с ротацией.
2. **SSE.** Прогресс расчёта приходит через SSE, а браузерный `EventSource` не умеет передавать заголовок `Authorization`.
3. **Хранение токена.** JWT в `localStorage` доступен любому XSS.
4. **Нет нужды.** Фронтенд и API на одном домене, сервис один: stateless-токены нужны для распределённых систем, а у нас модульный монолит.

Хранение сессий в БД переживает передеплой стенда. Заменяет «Spring Security + JWT» из первой версии описания.

## D-05

**Одна роль у учётной записи; без «войти как» и областей доступа** · Принято · 2026-10-22

Роли: администратор, организатор, преподаватель, студент. Переключатель «войти как…» не делаем: для демонстрации используем разные учётные записи. Права на данные определяются ролью и связью с сессией: организатор видит свои сессии, преподаватель и студент — сессии, где они участники. Настраиваемые администратором области доступа (UX-03 в первой версии) не входят в MVP.

## D-06

**Участник отмечает занятое время, а не свободное** · Принято (модель) / Предложено (правило для неответивших) · 2026-10-22

- **Что отмечает участник.** Занятые интервалы с уровнем важности: критический — жёсткое ограничение, средний и низкий — мягкое с разными весами. Неотмеченное время в рабочих часах считается доступным. Заменяет «зелёные и жёлтые слоты доступности» из первой версии описания.
- **Неответивший участник** считается доступным в рабочие часы, кроме известной занятости из учебного расписания. Организатор видит неответивших отдельно. Считать их недоступными нельзя: тогда все их события невыполнимы.
- **Статус ответа.** «Ответил без ограничений» и «не ответил» — разные статусы.

## D-07

**Справочник типов событий ведёт администратор** · Предложено · 2026-10-22

Типы — системный справочник, общий для всех сессий. Организатор не создаёт типы, но может поменять длительность, формат и состав у конкретного события. Это не ограничивает солвер: тип — только шаблон для заполнения полей события.

## D-08

**Частичная публикация исключена** · Предложено · 2026-10-22

UX-16 «Опубликовать часть расписания» убран: он требует выбора отдельных назначений, учёта опубликованных слотов как занятости и отдельных правил повторного расчёта. Вместо него UX-15 разрешает опубликовать вариант с неназначенными событиями после явного подтверждения; оставшиеся события решаются перестроением (UX-20).

## D-09

**Уведомления в MVP — только отметки в интерфейсе** · Предложено · 2026-10-22

Изменённые события и напоминания о сборе занятости показываются при входе в систему. Email-рассылки — после MVP: для них нужны SMTP, шаблоны и обработка ошибок доставки.

## D-10

**Модульный монолит с солверами на чистой Java** · Предложено · 2026-10-22

Один Spring Boot сервис. `domain-model` и солверы — отдельные Gradle-модули без Spring: отсутствие зависимости от Spring гарантирует компилятор; OR-Tools и Timefold не попадают в общий classpath; эксперименты запускаются консольной программой без приложения. Модули заводятся по мере работ. Фронтенд — отдельный репозиторий, а не папка в бэкенде.

## D-11

**Схема БД — только миграции Flyway** · Принято (миграции) / Предложено (соглашения) · 2026-10-22

Таблицы создаются вручную написанными миграциями, Hibernate только проверяет соответствие (`ddl-auto=validate`). Соглашения по именованию (единственное число, `snake_case`, учётные записи — таблица `account`, потому что `user` — зарезервированное слово PostgreSQL) и нумерации миграций — в [DEVELOPMENT.md](DEVELOPMENT.md#база-данных-и-миграции).

## D-12

**Стек: Java 25, Spring Boot 4.1** · Принято · 2026-10-22

Заменяет Java 21 и Spring Boot 3 из первой версии описания. Lombok используется.

## D-13

**OpenAPI генерируется из кода (springdoc)** · Предложено · 2026-10-22

Спецификация получается из контроллеров и DTO, поэтому не расходится с кодом. Чтобы фронтенд не ждал реализации, контракт вливается первым: контроллер с DTO и заглушкой, затем реализация ([DEVELOPMENT.md](DEVELOPMENT.md#api-контракт)).

**Общих инструкций для ИИ-агентов в репозиториях нет** · Принято · 2026-10-22

Каждый участник настраивает своих агентов сам. Общие правила работы — в этой документации, прежде всего в [DEVELOPMENT.md](DEVELOPMENT.md).
