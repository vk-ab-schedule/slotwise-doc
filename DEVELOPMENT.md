Как мы работаем с репозиториями, ветками, CI/CD, задачами и базой данных.

## CI/CD

Схема: [CICD_ARCHITECTURE.png](CICD_ARCHITECTURE.png). Стек: GitHub Actions, GitHub Container Registry, Ansible, Docker Compose. Для фронтенда и бэкенда процессы CI независимы, деплой централизован в `slotwise-infra`.

### Ветки

- `main` — итоговые версии спринтов. Меняется только релизным PR.
- `sprint/N` — интеграционная ветка текущего спринта. Создаётся от `main` в начале спринта.
- `feature/<issue>-<кратко>` и `fix/<issue>-<кратко>` — рабочие ветки от `sprint/N`.

### 1. Интеграция изменений

1. Разработчик создаёт ветку от `sprint/N`.
2. Открывает PR в `sprint/N`.
3. GitHub Actions собирает проект и запускает тесты. Если проверка упала, автор исправляет ветку, CI запускается снова.
4. После зелёного CI и одобрения ревьюера PR мержится в `sprint/N`.

### 2. Развёртывание текущей версии

1. Мерж в `sprint/N` запускает CI merge-коммита.
2. CI собирает Docker-образ и публикует его в GHCR с тегом по SHA коммита (и digest).
3. `slotwise-infra` разворачивает образ на общем стенде через Ansible и Docker Compose.
4. Стенд (4 vCPU / 8 ГБ): proxy с HTTPS и фронтендом, Spring Boot с солверами, PostgreSQL.
5. После деплоя — health-check и smoke-тесты.

Деплои выполняются последовательно, не параллельно.

### 3. Выпуск итоговой версии спринта

1. В конце спринта открывается PR `sprint/N → main`. На время выпуска деплои из `sprint/N` приостанавливаются.
2. Проходят CI и code review, PR мержится в `main`.
3. Образ из `main` собирается и публикуется в GHCR.
4. `slotwise-infra` разворачивает его, затем smoke-тесты.
5. После успешного релиза от `main` создаётся `sprint/N+1`, и активной веткой деплоя становится она.

### Правила CI/CD

1. **Защита веток.** На `main` и `sprint/*` разрешить мерж только через PR, с зелёным CI и одним одобрением; прямой push запретить.
2. **Хотфиксы.** Срочные исправления тоже идут через `sprint/N`, прямых PR в `main`, кроме релизного, нет. Тогда `main` всегда предок `sprint/N`, и миграции БД на общем стенде не расходятся.
3. **Способ мержа.** Рабочие PR — squash (одна задача = один коммит). Релизный PR — merge commit: при squash история `main` расходится со спринтовой веткой.
4. **Health-check.** Бэкенд отдаёт `/actuator/health` (с проверкой БД) без авторизации — его используют smoke-тесты.
5. **Один домен.** Reverse proxy отдаёт статику фронтенда и проксирует `/api` на бэкенд. Это нужно для cookie-сессий ([D-04](DECISIONS.md#d-04)) и избавляет от CORS.
6. **Секреты.** Пароль БД и данные первого администратора передаются переменными окружения из секретов GitHub или Ansible Vault; имена переменных фиксируются в README бэкенда.
7. **Ресурсы стенда.** Число одновременных расчётов ограничено настройкой бэкенда, чтобы CP-SAT не занимал весь CPU.
8. **Версия PostgreSQL** закреплена (мажорная версия) и одинакова локально, в Testcontainers и на стенде; тег `latest` не используется.
9. **Совместимость фронтенда и бэкенда.** Они деплоятся независимо на один стенд, поэтому ломающие изменения API сначала проходят через контракт (см. ниже) и вливаются согласованно.

## Задачи

- **Одна задача — одна issue** в репозитории, где будет код (документация — в `slotwise-doc`). У issue есть описание, критерии готовности и исполнитель.
- **Блоки** из [BLOCKS.md](BLOCKS.md) заводятся как issues; крупный блок можно разбить на под-задачи.
- **Статусы на доске:** New → Todo → In Progress → Review → Testing → Done. Review — открыт PR; Testing — смержено, проверяется на стенде; Done — проверено.
- **PR закрывает issue** строкой `Closes #N` в описании.

## Коммиты, ветки, PR

- **Ветки:** `feature/12-auth`, `fix/31-login-csrf`; в `slotwise-doc` — `docs/15-revision`.
- **Коммиты** — [Conventional Commits](https://www.conventionalcommits.org/) на английском: `feat(auth): add session-based login`. Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `ci`, `chore`. Область — модуль или пакет.
- **Заголовок PR** — в том же формате (он станет сообщением squash-коммита).
- **Описание PR:** что и зачем, как проверено, `Closes #N`, скриншоты для UI.
- **Ревью.** Бэкенд-PR ревьюит второй бэкендер; ревьюеры фронтенда и инфраструктуры — по договорённости. Ревьюер читает diff целиком.
- **Размер PR.** Небольшой: до ~400 строк изменений без учёта сгенерированного кода. Большую задачу делим на последовательные PR.

## API-контракт

1. Изменение API начинается с PR, в котором есть контроллер с DTO и заглушкой: спецификация генерируется из кода через springdoc ([D-13](DECISIONS.md#d-13)).
2. Ревьюер со стороны фронтенда подтверждает контракт.
3. Фронтенд генерирует TypeScript-типы из `/v3/api-docs` и работает на моках.
4. Реализация вливается отдельными PR без изменения контракта.

Ломающие изменения контракта согласуются с фронтендом заранее.

## База данных и миграции

- **Схему** создают только миграции Flyway в `app/src/main/resources/db/migration`; Hibernate работает с `spring.jpa.hibernate.ddl-auto=validate`.
- **Имена** в `snake_case`; таблицы в единственном числе (`account`, `planning_session`, `event`); внешние ключи — `<таблица>_id`; индексы — `ix_<таблица>_<колонки>`, уникальные — `ux_...`.
- **Ключи** — `bigint generated always as identity`.
- **Время** — `timestamptz`; перечисления — `varchar` с `check`.
- **Номера миграций** идут по порядку: `V1__create_account.sql`, `V2__create_university_data.sql`. Если два PR заняли один номер, тот, кто мержит вторым, переименовывает свою миграцию. CI это ловит: Flyway падает на дублирующейся версии.
- **Смерженные миграции не редактируются**, исправление — новой миграцией.
- **Данные на общем стенде** тестовые, базу можно пересоздать.

## Код бэкенда

- Пакеты по функциям, не по слоям (см. [ARCHITECTURE.md](ARCHITECTURE.md#пакеты-в-app)).
- DTO — Java records. Сущности JPA наружу из контроллеров не отдаются.
- Внедрение зависимостей через конструктор (`@RequiredArgsConstructor`).
- Lombok на JPA-сущностях: `@Getter`, `@Setter`, `@NoArgsConstructor(access = PROTECTED)`. Без `@Data` и `@EqualsAndHashCode`: они ломают equals/hashCode у сущностей и ленивую загрузку.
- `domain-model` и солверы не зависят от Spring; время и случайность передаются явно (seed, `Clock`).
- Ошибки — исключения предметной области, превращаемые в Problem Details в одном обработчике.
- Тест на каждую новую функцию: юнит-тесты для логики, интеграционный тест с Testcontainers для API.

## Готовность задачи

Задача считается сделанной, когда:
- код смержен в `sprint/N`, CI зелёный;
- тесты написаны;
- контракт API обновлён, если менялся;
- задеплоенная версия проверена на стенде;
- документация обновлена, если поменялось поведение, модель или решения.

## Документация

- `slotwise-doc` использует ветку `main` и PR из веток `docs/*`.
- Изменение поведения продукта (UX-сценарии, модель, решения) мержится после одобрения команды в PR.
- Принятые решения записываются в [DECISIONS.md](DECISIONS.md).
- Вики репозитория содержит только ссылку на репозиторий.
